# EDGEmat: notes for Claude sessions

EDGEmat is the EDGEmodders material editor for Cyberpunk 2077: a standalone VS Code extension in the EDGE family (`edgemodders.edgemat`) and an MCP server, so a modder edits materials in the UI or tells REDagent or Claude "make this jacket red". Multilayered setups (`.mlsetup`, `.mltemplate`, `.mlmask`) first, then `.mi` and `.mt`. Read [docs/design.md](docs/design.md) first. It reads and writes game files through REDbridge, like REDcode.

## Conventions

- Same as the sibling repos (see REDcode's and REDnode's CLAUDE.md): commit straight to `main` in small commits and push; plain, short sentences; tables for facts; mark anything unverified.
- **Git identity:** per repo, `CyberbuildsAI` with the GitHub no-reply email (`340969962+CyberbuildsAI@users.noreply.github.com`). Never change the global identity.
- **Never commit game files**, WolvenKit binaries, or data extracted from the game.
- **License boundary:** this repo is MIT. Talk to REDbridge (GPL-3.0) only as a separate process; never link it or copy WolvenKit code here. Needs from the bridge go to REDbridge as issues labelled `request`, with the shape that would work.
- **Do not change REDcode or REDbridge from here**; other sessions work in them.
- **MlsetupBuilder (GPL-3.0) is studied, never copied.** Only the M0 spec session reads its source, and writes what it learns in its own words in `docs/design/behavior.md`. Build sessions work from that spec and never open MlsetupBuilder's source. No code, text or data from it in this repo. GPL logic worth reusing as code goes into REDbridge with attribution.
- **The mission decides UI questions:** modding for everyone, especially non-coders; easy, fun, fast. Plain words first, raw values one click away. Every feature ships in the UI and the MCP server together. AI is optional: no telemetry, and no network calls until an assistant or an AI service the user chose connects (Generate calls an image service only when pressed, with the user's own key).
- Keep `extensions/edgemat/src/core` free of VS Code imports; the MCP server bundles it.
- **House style** is the HUD look from REDnode's design doc, and the REDnode HUD theme in REDcode is the default theme for any VS Code UI.
- **Progress log:** `docs/progress.md` is how the owner catches up without asking. Update it in the same commit as any status change: the log, decisions, findings, requests and the owner's to-dos.
- **Changelog:** `docs/changelog.md` is the one changelog, kept as REDnode's is: each change a modder would notice gets a line under **Unreleased** (**New**, **Changed**, **Fixed**, **Other**) in the same commit. Release notes and the extension's `CHANGELOG.md` are generated from it (`tools/release/notes.mjs`; steps in `docs/dev-setup.md`, "Releasing").
- **Release gate (the owner's rule):** no release (Make a release, a Marketplace, Open VSX, npm or Nexus upload) until every test in `docs/testing.md` for the builds since the last release has passed. Untested or failed stops it: say what is still open, even when asked to release.
- **Starting a release:** Claude starts a release run only when the owner asks in chat, with `gh workflow run release.yml --ref main -f release=true -f nexus=true` (the owner may also start it by hand). Steps in `docs/dev-setup.md`, "Releasing".
- **README at each release (the owner's rule, 2026-11-03; the same in every Edgemodders repo):** before an EDGEmat release run, update `README.md`'s status line (`**Status: <version> preview released on <date>** ...`, with what is new worth a line) and draw the status badge again (`tools/brand/badges.py`: the `status` entry, `"<version> preview"`, then `python -I tools/brand/badges.py docs/assets/brand/badges`, or `tools/brand/render.ps1` for every brand image; the README's `<img alt>` too). The version is the extension's (`extensions/edgemat/package.json`, kept in step by `tools/version.mjs`). `release.yml` stops before building when they do not name it (`tools/release/readme-check.mjs --version`, a copy of REDnode's kept identical: copy it again from there, never edit it here). `release-wardrobe.yml` has no such check, since the README's status is EDGEmat's; Wardrobe Designer's own page is `docs/wardrobe-designer.md`. Before this rule the badge said 0.3 and its alt "scaffold".
- **Nexus Mods** (page 35422, live since 0.3.0) is kept through Nexus's v3 API since 2026-10-25, as REDnode's and REDagent's pages are: the Nexus tool (in EDGErepo, `../EDGErepo/tools/nexus/`; the release workflows clone it at the tag `v1`; change it there), `nexus/nexus.json`, the organisation secret `NEXUS_KEY` in CI, a DPAPI key file on the dev PC (never print the key or put it on a command line). The release workflow's **Update Nexus Mods** box uploads the Nexus zip as the main file's new version with **Mod Manager Download off** (a VS Code extension, not a game mod; `"modManager": false` in nexus.json), archives the old one, adds the changelog and pushes `nexus/description.bbcode`. It stops before building if the description changed on Nexus since the last pull: `npm run nexus:pull`, merge, commit. Screenshots the owner uploads on Nexus appear in the description as `staticdelivery.nexusmods.com` links; keep them. No credit to the owner's own account (Cyberbuilds) in the page's credits.
- **Tests:** `docs/testing.md` lists every test with steps to rerun it, expected results and the last result. Add a test there when it is first run.
- **Docs site:** `docs/` is published by GitHub Pages through `.github/workflows/pages.yml`. `docs/index.md` is the landing page (document ledger and roadmap status); add every page to `nav` in `docs/_config.yml`. Brand images come from `tools/brand/render.ps1`. Record every tool install in `docs/dev-setup.md`, with versions and exact commands.
